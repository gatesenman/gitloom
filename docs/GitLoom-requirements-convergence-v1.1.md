## 1. 产品定位

**一句话**：GitLoom 是给“一个项目由多个 Git 仓库组成”的复杂项目用的 **Git 全生命周期桌面工具**——从拿到代码、看懂改动、把好质量，到自动沉淀项目知识，都在一个本地应用里完成。

**为什么需要它**：
- 现在的改动量（自己写的、同事写的、AI 写的）已经多到“逐行读不过来”；需要先用图看结构、看风险，再决定读哪几行。
- 一个产品常拆成前端、后端、SDK、配置、文档等 5～30 个仓库；现有 Git 客户端以“单仓库”为中心，跨仓库的同步、提交、检查全靠人记。
- 代码审查、架构图、安全扫描、项目文档散落在多个工具和网站上，结果互相不认识。

**五个支柱（用户原意）**
| # | 支柱 | GitLoom 的承诺 |
|---|---|---|
| ① | 看懂改动 | 改动太多读不完时，先给图（结构/调用/影响范围）和阅读路线，再进代码；不论改动来自自己、他人还是 AI |
| ② | 全局多仓库生命周期 | “项目”是一等公民：多仓库总览、批量同步、跨仓库提交、统一检查 |
| ③ | 内置本地自动化 | 代码变化时自动做事，首个场景：按 Karpathy “LLM Wiki”模式自动更新**项目级、仅本地**的知识库 |
| ④ | 内置分析与把关 | 静态分析、架构可视化、设计审查、代码知识图谱、代码审查、安全扫描、Better Harness（AI 协作流程体检） |
| ⑤ | 不删功能 | 现有功能只修复、只重新归位，一个都不删 |

**不做什么（边界）**：不做 IDE（不内置编辑器/终端/LSP，继续“在 VS Code/终端中打开”）；不做云服务（默认全部本地运行，AI 只调用用户自己配置的模型）；不替代 CI（但可生成可放进 CI 的配置）。

**底层原则（贯穿所有模块）**
1. **证据优先**：每一条结论（图上一条连线、一条审查意见、一个风险）都要能点回“哪个文件哪一行 / 哪条 git 命令”；证据不足就明说“不确定”，不编。（来自 QGraphFlow、architecture-visualization、Better Harness 的共同做法）
2. **确定性在前、AI 在后**：能用程序算准的（选哪些文件、行号定位、依赖关系）用程序算；AI 只负责解释、归纳、判断。（来自 OpenCodeReview 的混合架构，GitLoom v0.5 可视化已是这个思路）
3. **本地、离线可用**：没有 AI 也能用（静态结果），有 AI 是增强；密钥只存本机。
4. **项目级优先**：所有分析都可以在“单仓库”和“整个项目（多仓库）”两个范围运行。

## 3. 参考资料研读：各自提供什么、GitLoom 采纳什么

集成方式三种，后文统一用这三个词：
- **内置技能/提示词**：把参考项目的方法论（SKILL.md、检查清单、输出模板）改写为 GitLoom 内置的 AI 提示词与结果格式，由 GitLoom 自己调用用户配置的模型。不依赖外部安装。
- **调用命令行（CLI）**：用户机器上装了该工具时，GitLoom 在后台调用它并把结果画到界面上；没装时给安装引导，并退回到内置能力。
- **自行实现**：用 GitLoom 现有的 TypeScript 代码（tree-sitter 解析、React Flow 画图等）重写核心逻辑。

### 3.1 architecture-visualization（Qoder 插件，许可待确认）
**它是什么**：13 个“架构场景技能”的集合，没有代码提取器，全靠 AI 读项目后写出图。分三层：路由（explore）→ 9 个场景（系统建模、流程、依赖影响、部署拓扑、演进规划、风险与质量审查、遗留系统、面向听众讲解、架构健康度）→ 3 个出图基础（C4/Structurizr、Graphviz、Draw.io）。另有共享的**证据模型**：节点/连线都带 `sourceRefs`（源码位置）与 `confidence`（高/中/低/未知），证据分 code/contract/config/data/runtime/document/human-assumption 七类；以及 Mermaid / DOT / Structurizr 三个预览器。

**GitLoom 采纳**
| 采纳项 | 方式 | 落点 |
|---|---|---|
| 证据模型（sourceRefs + 置信度 + 证据类别）作为 GitLoom 所有图和报告的统一数据格式 | 自行实现（扩展现有 `shared/viz.ts`） | 架构与知识、质量把关 |
| 9 个场景作为“我想回答什么问题”的入口菜单（比按图类型选更好懂） | 内置技能/提示词 | 架构与知识 → “提问式出图” |
| 架构健康度（图是否过时、能否追溯到代码）| 内置技能 + 自行实现“过时检测”（图里引用的文件/符号是否还存在） | 架构与知识、体检报告 |
| 风险与质量审查（质量属性、技术债、架构风险清单） | 内置技能/提示词 | 质量把关 → 架构审查 |
| 演进规划（目标态 vs 现状差距、架构决策记录 ADR） | 内置技能/提示词，P2 | 架构与知识 |
| 部署拓扑（从 Dockerfile、k8s、compose 识别运行位置） | 内置技能 + 少量自行实现的配置解析，P2 | 架构与知识 |
| 导出 Structurizr DSL / DOT / Mermaid / Draw.io | 自行实现（现已支持 Mermaid、PlantUML，补 DSL、DOT、drawio） | 架构与知识 → 导出 |
| 预览器（打开仓库里已有的 .mmd/.dot/.dsl 文件） | 自行实现（Mermaid 本地渲染；DOT 用 wasm 版 Graphviz） | 架构与知识 |

### 3.2 design-review（Qoder 插件）
**它是什么**：前端“设计契约与实现质量”审查，8 个技能：DESIGN.md 审查、完整设计 QA 编排、UI 与设计稿对齐、截图对比（视觉回归）、可访问性、组件库一致性、设计债（硬编码颜色/内联样式/随意 Tailwind 值）、从代码提取设计系统。脚本化部分用 Node + Playwright，输出写到项目 `.design-qa/`（Markdown + JSON）。**发现项格式**统一：严重级别、类别、证据、现状、期望、影响、修复建议、验证方法、负责人。

**GitLoom 采纳**
| 采纳项 | 方式 | 落点 |
|---|---|---|
| “发现项”统一格式 → 作为体检报告里所有问题（审查/安全/设计/架构）的通用字段 | 自行实现 | 质量把关 |
| 设计债扫描（硬编码颜色、内联样式、令牌漂移）——纯静态、无需浏览器 | 自行实现（基于 tree-sitter + 正则，只扫改动文件或全仓） | 质量把关 → 设计审查 P1 |
| DESIGN.md 审查（检查设计契约是否完整、令牌是否被代码引用） | 内置技能/提示词 + 静态统计 | 质量把关 → 设计审查 P1 |
| 组件库一致性（是否绕开设计系统组件直接写原生元素） | 内置技能/提示词 | P2 |
| 可访问性、截图对比、UI 对齐（需要 Playwright 和浏览器） | 调用 CLI：检测到用户安装了 design-review 插件脚本 + Playwright 时调用其 `run-design-qa.mjs`，读取 `.design-qa/*.json` 展示 | P2 |
| 仅对“有前端代码”的仓库显示设计审查 | 自行实现（按文件类型判断） | 质量把关 |

### 3.3 QGraphFlow 0.0.7（MIT）
**它是什么**：一个 AI 技能 + Node 脚本，从源码/数据结构/配置生成 **11 类交互式软件图**（平台能力架构、工程分层、组件关系、流程、时序、ER、部署、类、状态、用例、数据流），每条关系标明证据类别并记录源码行号；产出**单个离线 HTML**（可搜索、核对证据、解锁编辑、导出 SVG/PNG），脚本和查看器不发网络请求。有严格的 Graph JSON 契约、校验器（validate-graph）、ELK 布局编译（含宽高比折叠、主路径自上而下等规则）和验收清单。

**GitLoom 采纳**
| 采纳项 | 方式 | 落点 |
|---|---|---|
| 补齐 GitLoom 缺的图类型：**ER 图、部署图、用例图、数据流图、平台能力图**（现有 8 种：架构、模块依赖、调用、类、影响范围、控制流、时序、状态） | 内置技能/提示词（AI 按 QGraphFlow 的类型规范输出 Graph JSON）+ GitLoom 自己的渲染 | 架构与知识 |
| Graph JSON 契约与校验规则（引用完整性、分组归属）→ 吸收进 GitLoom 的 AI 输出校验（现有 zod 校验） | 自行实现 | 全部图 |
| 布局规则（宽高比 1:1.6 带外自动折叠、流程主路径自上而下） | 自行实现（并入现有 ELK 布局管线） | 看懂改动、架构与知识 |
| “导出离线 HTML 分享”（一个文件，打开即可交互） | 调用 CLI（可选）：用户装了 qgraphflow 时直接调用 `generate-viewer.mjs`；同时 P2 自行实现 GitLoom 版离线 HTML | 导出 |
| 引导式提问（空白输入时先问“想回答什么问题”） | 内置技能/提示词 | 架构与知识 → 提问式出图 |

### 3.4 product-management（Qoder 插件）
**它是什么**：产品经理工具箱（PRD、用户故事拆解 INVEST、竞品分析、RICE/ICE/MoSCoW/Kano 排序、Release Notes、反馈分析、路线图、指标复盘、脑暴）。
**GitLoom 采纳**：主要用于**本文档的方法**（用户故事 + 验收标准、MoSCoW 定 P0/P1/P2）。产品功能上只采纳一项：**Release Notes / 变更日志生成**（多渠道：对用户 / 对内部）——GitLoom 已有“PR 描述 + Changelog”AI 动作，升级为“按版本、跨仓库生成 Release Notes”，方式：内置技能/提示词，P1，落在 工作区 → 发布。

### 3.5 Karpathy · LLM Wiki 模式
**它是什么**：让 AI **持续维护**一个互相链接的 Markdown 知识库，而不是每次提问都重新检索原文（区别于 RAG）。三层：**原始资料**（只读）→ **Wiki**（AI 全权写）→ **规则文件 schema**（告诉 AI 怎么组织，如 AGENTS.md）。三种操作：**Ingest 吸收**（新资料进来，更新 10～15 个相关页面并记日志）、**Query 提问**（先读 index 再答，好答案可回存为新页）、**Lint 体检**（找矛盾、过时结论、孤儿页、缺失页面、缺交叉引用）。两个特殊文件：`index.md`（按类别的目录，每页一句话摘要）和 `log.md`（只追加的时间线，每条以 `## [日期] 操作 | 标题` 开头）。

**GitLoom 采纳（已定：项目级、仅本地，不提交进任何仓库）**
| 采纳项 | 方式 |
|---|---|
| 存放位置：`<应用数据目录>/projects/<项目ID>/wiki/`（不在任何仓库工作区内，天然不会被提交）；可在设置里改到用户指定目录（如一个 Obsidian 库） | 自行实现 |
| 原始资料 = 项目内所有仓库的提交、diff、README/docs、GitLoom 的分析结果（架构图、体检报告）；只读 | 自行实现 |
| 规则文件 `wiki/SCHEMA.md`：GitLoom 提供默认模板（页面类型：仓库页、模块页、概念页、决策页、变更摘要页），用户可编辑 | 内置技能/提示词 |
| Ingest：由“自动化”模块触发（提交后 / 拉取后 / 定时），**增量**：只处理新提交，更新相关页面 + `index.md` + `log.md` | 自行实现调度 + 内置提示词 |
| Query：在 GitLoom 的 AI 助手里“问项目百科”，回答带页面引用；可一键“存为新页” | 自行实现 |
| Lint：每周或手动，输出体检结果到 Wiki 的 `lint/` 页并进体检报告 | 内置提示词 |
| 页面带 YAML 头信息（来源提交、更新时间、置信度），兼容 Obsidian/Dataview | 自行实现 |
| Wiki 目录本身用一个**本地私有 git 仓库**做版本历史（Karpathy 建议），可回看/回滚 AI 改了什么 | 自行实现 |

### 3.6 OpenCodeReview（阿里巴巴，Apache-2.0，CLI 名 `ocr`）
**它是什么**：AI 代码审查命令行。核心是“确定性工程 + Agent 混合”：程序负责**精确选文件、相关文件打包（分包并发审查）、按文件特征匹配规则、独立的评论定位与反思模块**；Agent 负责动态读上下文。内置多语言规则（空指针、线程安全、XSS、SQL 注入）。支持 `ocr review`（工作区/分支区间/单提交）、`ocr scan`（整文件审计）、`--format json` 输出、会话续跑、**委托模式**（不配模型，由外部 Agent 执行）、MCP、CI 集成。要求 Git ≥ 2.41。精度高、召回偏低（宁少勿错）。

**GitLoom 采纳**
| 采纳项 | 方式 |
|---|---|
| **首选：调用 CLI**。检测到 `ocr` 时，“代码审查”直接跑 `ocr review --from/--to/--commit ... --format json --output`，把行级意见画在 Monaco 差异里；支持续跑、整仓 `ocr scan` | 调用 CLI |
| 把 GitLoom 已配置的 AI 服务商传给 ocr（环境变量，密钥不落盘），用户不用再配一遍 | 自行实现 |
| 未安装时：一键安装引导（`npm i -g @alibaba-group/open-code-review`）；或退回 GitLoom 现有“AI 审查暂存区”（升级为借鉴其做法：文件分包、行号由程序定位、二次反思） | 调用 CLI + 自行实现兜底 |
| 意见状态“已修复 / 忽略”，按会话保存（借鉴其 Session Viewer） | 自行实现 |
| 多仓库：对项目内每个有改动的仓库并发审查，汇总进体检报告 | 自行实现 |

### 3.7 Better Harness（QoderAI）
**它是什么**：给“AI 编程助手的工作流程”做体检（Harness = 套在 AI 外面的约束和反馈机制）。按 **Agent 工作环** 5 个维度评估：任务理解（AGENTS.md、规格、DESIGN.md）、受控执行（Skills、命令、MCP、沙箱）、变更验证（测试、lint、钩子）、可靠交付（人审、CI、回滚）、经验沉淀（可复用技能、记忆）。证据来自项目文件和 AI 会话记录，**缺证据就明说**；输出报告（HTML + Markdown + findings.json），每条发现带影响、修复范围、验收检查；可看多次报告的趋势。运行在宿主 Agent 里（Claude Code、Codex、Cursor、Qoder 等）。

**GitLoom 采纳**
| 采纳项 | 方式 |
|---|---|
| “AI 协作体检”：GitLoom 自己就能拿到的证据（是否有 AGENTS.md/CLAUDE.md/.cursor/rules、测试与 lint 配置、Git 钩子、CI 文件、提交里 AI 生成比例的线索），按 5 维度出静态评分卡 | 自行实现 + 内置提示词 |
| 深度版：检测到用户的 Agent 已装 better-harness 时，读取其 `findings.json` / `report.md`（如 `.claude/better-harness/`）并纳入体检报告与趋势 | 调用 CLI / 读取产物 |
| 每条发现的“修复动作”可一键变成 Git 钩子模板或 AGENTS.md 片段（与自动化模块联动） | 自行实现 |
| 历史趋势（多次体检对比） | 自行实现 |

## 4. 模块与用户故事

### 4.0 模块结构（在提案基础上的细化）
提案的 5 个模块保留，参考资料带来三点调整：
1. **新增“日常 Git”作为底座**（不是第 6 个大模块，而是每个仓库里始终可见的工作台：变更、历史、分支）。原因：现有大量 Git 生命周期功能必须有家，且它们是最高频操作；塞进“工作区”会让总览变重。
2. **“质量把关”的核心产物叫“体检报告”**，所有检查共用 3.2 的“发现项”格式和 3.1 的证据模型；“AI 协作体检（Better Harness）”放进质量把关的一个分项，而**它给出的修复动作落到“自动化”**执行。
3. **“架构与知识”分两半**：看结构（图、知识图谱）和存知识（LLM Wiki）；两者共享一个“代码知识图谱”底层数据。

```
                   ┌──────────── 工作区（项目 = 多仓库）────────────┐
 顶层导航：         │ 总览 · 跨仓库变更 · 批量操作 · 发布               │
                   ├───────┬──────────┬───────────┬───────────────┤
                   │看懂改动│架构与知识 │ 质量把关   │ 自动化          │
                   └───────┴──────────┴───────────┴───────────────┘
 每个仓库内：        日常 Git（变更 / 历史 / 分支）+ 「更多」（变基、二分、追溯、子模块、PR、AI 助手）
 全局：             设置（AI 服务商、外观、扫描、Git 配置）· 命令面板 Ctrl+K · 命令日志
```
范围切换器：每个模块顶部都有“当前仓库 / 整个项目 / 选中的几个仓库”。

### 4.5 自动化（本地钩子 + Harness）

## 7. 非功能要求
- **性能**：24 仓库首屏 ≤2 s；体检/Wiki/图谱全部后台运行、可取消、不阻塞日常 Git。
- **成本透明**：凡调用 AI 的自动化，运行前可估算、运行后记录 token；可设每日上限。
- **隐私**：默认不上传任何内容；发送给模型前可预览；Wiki 与体检存档只在本机。
- **可降级**：外部工具（ocr、Semgrep、better-harness、Playwright、qgraphflow）均为“检测到才启用”，缺失时有中文说明与内置兜底。
- **许可**：QGraphFlow 为 MIT，可改写其提示词与脚本并保留署名；OpenCodeReview 为 Apache-2.0，以调用 CLI 为主；architecture-visualization、design-review 的插件包内未声明许可证，Better Harness 需核对仓库许可，均需在改写前确认（已决，见 §8）。

## 9. 术语表
| 词 | 白话解释 |
|---|---|
| 仓库（repo） | 一个独立的 Git 版本库；一个“项目”可包含多个仓库 |
| diff / 改动 | 两个版本之间的差别 |
| 钩子（hook） | Git 在提交、推送等时刻自动运行的脚本 |
| 静态分析 | 不运行程序、只读代码就能发现问题的检查 |
| 知识图谱 | 把文件、函数、模块等当点，把“调用/依赖/修改”当线，存起来可查询 |
| LLM Wiki | 由 AI 持续维护的项目知识库（Markdown 文件集合） |
| C4 | 一种画软件架构的分层方法：系统→容器→组件→代码 |
| Harness | 套在 AI 编程助手外面的规则、检查和反馈机制 |
| SARIF | 静态分析结果的通用文件格式 |
| MCP | 让 AI 助手调用外部工具的一种标准接口 |
| 置信度 | 结论有多可靠：高（有代码证据）/中/低（AI 推断）/未知 |
